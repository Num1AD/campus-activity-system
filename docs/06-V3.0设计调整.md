## 6.1 本轮为什么调整

需求来源与前两轮不同：V1.0 来自工程意图，V2.0 来自用户访谈，本轮**来自模拟运行数据**。判断链条是「数据现象 → 本组核实 → 是否改」，三步都要留痕。

| 数据现象（含口径） | 对照本组 V2.0 的核实结果 | 本轮处理 |
|---|---|---|
候补申请 876 个，仅 130 个递补成功（14.8%），746 个（85.2%）始终停在 waiting；递补等待中位 1 085 分钟，且递补只由取消触发（间隔恒 120 秒） | 报名表只有 `status` 与 `queued_at`，**没有状态变更历史**；「我的活动」只显示当前状态，看不到"什么时候变的"；全系统**无任何提醒机制** | **R3-01 报名状态变化可见** |
反馈中 26 条涉及状态不可见或候补结果无通知（如「有次候补转成功了，隔了两天打开页面才发现」） | 同上 | 同上 |
`duplicate` 126 条，**100% 发生在同活动已成功之后**；反馈 19 条涉及"不确定是否提交成功" | `handleRegister` 请求在途期间按钮仍可点击，双击即发两次请求；重复提交返回 400「不能重复报名」，被当作错误弹出 | **R3-02 提交结果明确与防重复** |
反馈 26 条涉及活动查找，其中频次最高者（10 次）指向"列表信息不足" | 我们的卡片已显示地点、起止时间、已报名/容量、状态标签与候选资格，并已按开始时间升序；**该现象在本组不存在**。分类筛选因活动模型无 `category` 字段，新增该维度超出本轮 | **不做**（见 6.7） |
满员分支耗时中位 1 308 ms（模拟平台数据） | 本组为 SQLite 单机、数据量级小两个数量级，**无法在同等条件下复现** | **不做**（见 6.7） |

## 6.2 需求与工程意图

### 需求

**R3-01 报名状态变化可见**
学生能够查到本人报名的每一次状态变化（何时提交、何时进入候补、何时被递补或审核），并能看到当前候补排队位置；由教师或系统触发的变化要有未读提示。

**R3-02 提交结果明确、避免无意重复**
学生提交报名时，处理期间按钮不可重复点击；提交结果（成功 / 进入候补 / 等待审核 / 已报过）要给出明确且可理解的说明，重复提交不再表现为一条看不懂的错误。

### 本轮工程意图

- **主要目标**：让学生不必反复进入页面即可确认报名状态的每一次变化，同时消除"不知道是否提交成功"导致的重复提交。
- **实现范围**：数据层新增状态变更记录表与已读位置字段；后端新增查询与标记已读接口、在 `my-activities` 中补充候补位置；前端新增未读徽标、状态时间线、在途保护与提示文案。
- **非目标**：不改名额统计口径、不改递补规则、不改角色权限边界、不新增活动分类维度、不做性能优化。
- **完成依据**：新增自动化用例覆盖"变更被记录""未读数计算与清零""候补位置正确""重复提交返回明确状态"；前端实测按钮在途禁用与时间线展示；原有 38 条用例全部通过。

## 6.3 数据设计调整

### 新增表 `registration_events`

记录报名的每一次状态变化。**不设指向 `registrations` 的外键**，因为取消报名与审核拒绝都会删除报名记录，外键会导致历史断裂。

```sql
CREATE TABLE IF NOT EXISTS registration_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    activity_id INTEGER NOT NULL,
    user_id     INTEGER NOT NULL,
    from_status TEXT,                                  -- NULL 表示首次提交
    to_status   TEXT    NOT NULL,                      -- pending / confirmed / waitlisted / removed
    reason      TEXT    NOT NULL,                      -- 见下表
    needs_notice INTEGER NOT NULL DEFAULT 0,           -- 1=由教师或系统触发，需要提醒学生
    created_at  TEXT    NOT NULL DEFAULT (datetime('now', 'localtime'))
);
CREATE INDEX IF NOT EXISTS idx_evt_user     ON registration_events(user_id, created_at);
CREATE INDEX IF NOT EXISTS idx_evt_activity ON registration_events(activity_id);
```

### 状态变化的记录点

| 触发动作 | from_status | to_status | reason | needs_notice |
|---|---|---|---|---|
学生提交报名（有名额） | NULL | confirmed | `apply` | 0 |
学生提交报名（满员进候补） | NULL | waitlisted | `apply` | 0 |
学生提交报名（需审核） | NULL | pending | `apply` | 0 |
教师审核通过且有名额 | pending | confirmed | `review_approved` | **1** |
教师审核通过但满员 | pending | waitlisted | `review_waitlisted` | **1** |
教师拒绝 | pending | removed | `review_rejected` | **1** |
学生取消 / 撤回 / 退出候补 | 原状态 | removed | `withdraw` | 0 |
取消引发递补 | waitlisted | confirmed | `promoted` | **1** |

> `needs_notice` 的设计理由：提醒只针对**不由本人发起**的变化。学生自己报名不需要被提醒，但审核结果与递补必须提醒——这正是数据里 85.2% 候补无果、用户"要自己查"的痛点所在。

### `users` 表新增已读游标

```sql
events_seen_id INTEGER     -- 该学生已读到的状态变化事件 id，服务端保存
```

**用事件 id 而不是时间做游标**：时间只精确到秒，同一秒内产生的多条事件按时间比较会被漏判（实现时实测踩到：学生点开页面的同一秒内教师完成审核，未读没有出现）。id 严格递增、没有并列，不存在这个问题。

放在服务端而不是浏览器本地：换设备或换浏览器后未读状态仍然正确。演示数据在写入时把该字段设为种子事件的最后一个 id，避免首次打开时把历史事件全算作未读。

**游标推进上限由客户端决定**：标记已读时带上 `until`（本次已加载到的最大事件 id），只在客户端看到的范围内推进。否则「先取列表、再标已读」这两步之间若恰好产生新事件，会被一并标成已读，提醒悄悄丢掉。游标本身只前进不后退，重复调用或传入更小的 `until` 都不会把已读位退回去。

### 名额口径不变

仍只统计 `confirmed`；`registration_events` 是**只写不读的业务日志**，不参与任何名额判定，因此不会影响 V2.0 已有的候补与递补规则。

## 6.4 接口调整

### 新增

| 接口 | 说明 |
|---|---|
`GET /api/my-registration-events` | 返回本人全部状态变化事件（含活动标题、前后状态、原因中文说明、时间），并给出 `unread_count`；学生专属 |
`POST /api/my-registration-events/read` | 推进已读游标；可带 `until`（客户端已加载到的最大事件 id），只把确实看到的事件标为已读，返回推进后的真实未读数。不带 `until` 时推进到当前最新，兼容旧调用 |

### 变更

| 接口 | 变化 |
|---|---|
`GET /api/my-activities` | 学生视角的每条记录新增 `queue_position`（候补排队位置，1 起）与 `waitlist_total`（候补总人数）；非候补状态为 null |
`POST /api/activities/{id}/register` | 重复报名由 **400** 改为 **409 Conflict**，响应体补充 `current_status`（当前报名状态中文），语义上"已报过"不是请求错误，而是与当前资源状态冲突 |

### 不变

报名、取消、审核、名单查询的路径与鉴权边界全部不变；其他角色调用新接口返回 403（fail-closed）。

## 6.5 前端交互调整

**R3-01**

1. 顶部「我的活动」按钮右侧显示未读徽标（`N` 条新变化），无未读时不显示。
2. 「我的活动」视图的学生卡片增加「状态变化」展开区，按时间正序列出：提交报名 → 进入候补 → 审核通过/拒绝 → 递补成功，每一步带时间与原因中文说明。
3. 候补中的卡片显示「当前排在第 N 位（共 M 人）」。
4. 进入该视图并展开后调用标记已读接口，徽标清零。

**R3-02**

5. `regBusy` 集合按活动 id 记录在途请求：请求期间按钮禁用、文案改为「处理中…」，从源头避免双击重复提交。
6. 提交结果提示按类型区分：
   - 成功：「报名成功，可在「我的活动」查看状态变化」
   - 进候补：「名额已满，已进入候补队列（当前第 N 位）」
   - 待审核：「报名已提交，等待组织教师审核」
   - 已报过（409）：「你已报名该活动，当前状态：正式参加」，并自动刷新为可取消状态
7. 失败提示附带下一步指引，不再只弹原始错误文本。

## 6.6 与原有业务的关系

| 原有能力 | 本轮是否受影响 | 说明 |
|---|---|---|
名额只算正式参加 | 不变 | 事件表不参与统计 |
取消触发递补（同一事务） | 不变 | 递补成功时额外写入一条 `promoted` 事件 |
候补按 `queued_at` 排序 | 不变 | 排队位置只读该字段计算 |
审核先资格后名额 | 不变 | 审核结果额外写入事件 |
教师只看本人活动名单 / 管理员只读 | 不变 | 新接口只面向学生本人，越权返回 403 |
演示数据可现场演示三种报名状态 | 增强 | 演示报名同时写入事件，打开即可看到时间线 |

## 6.7 取舍说明（考虑过但不做）

**活动分类筛选**：模拟数据中反馈有 26 条涉及活动查找，但频次最高的一条（10 次，「标题看着差不多」）指向列表信息不足，而本组卡片已展示地点、时间、已报名人数与状态，并已按开始时间排序，该现象在本组不成立。分类筛选需要先为活动模型新增 `category` 字段并重建分类体系（改表 + 发布表单 + 接口 + 前端 + 演示数据），属于新增业务维度而非问题修复，超出本轮范围。

**性能优化**：模拟数据中满员分支耗时中位 1 308 ms，是成功路径（215 ms）的六倍，看似存在名额判定的性能问题。但该数据来自统一模拟平台，本组为 SQLite 单机、活动与报名量级小两个数量级，无法在同等条件下复现，缺乏可比基线，本轮不作处理，留作后续观察项。

## 6.8 验证方式

| 验证内容 | 方式 |
|---|---|
状态变化被正确记录 | 自动化用例：报名 / 进候补 / 审核 / 递补 / 取消各触发一次，核对事件表条数与字段 |
未读数计算与清零 | 自动化用例：学生触发教师操作后未读数 +1，调用标记已读后归零 |
候补位置正确 | 自动化用例：三人依次进候补，核对排队位置为 1/2/3 |

原有功能未退化 | 回归 V2.0 全部 38 条用例 |
效果对比 | V2.0 与 V3.0 各跑同一组操作，对比"能否得知状态变化时间"与"重复请求次数" |

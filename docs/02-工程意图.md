# 02 工程意图 —— 校园活动管理系统 V1.0

> 来源：实验一《基于工程意图的软件迭代开发》实验要求"（二）形成工程意图" + 教材《现代软件工程》第 1 章 1.4 节
> 对应报告章节：三、工程意图

## 术语口径（教材原意，忠实引用）

教材定义：**工程意图把"想让 AI 做什么"变成可执行、可约束、可验证的软件变化说明**，包含四要素：**目标、范围、非目标、验收依据**。

IDE（Intent-Driven Engineering，意图驱动工程）四步链：

1. 变更依据 —— 用户反馈/业务事实；
2. 工程意图 —— 只做 X，不改变 Y；
3. 受控实现 —— 修改限定在工程意图范围内，限制 AI 候选修改范围；
4. 工程事实 —— 用代码差异、构建、测试和评审确认结果。

关键纪律：AI 产出仅作候选；即使 AI 修改后测试全部通过，**越界修改也不能直接接受，必须回到工程意图验证**。

## 工程意图表（按教材四要素 + 实验五问展开）

| 要素 | 内容 |
|---|---|
| **建设目的**（为什么建） | 当前活动信息靠线下通知与人工统计，学生难以及时发现活动、教师无法掌握参与情况。建设 V1.0 使"教师发布 → 学生浏览 → 报名参与 → 教师掌握情况"这一基本业务过程线上化。 |
| **本轮范围**（做什么） | 完成 REQ-01~08 对应的用户、活动、报名三个模块；系统本地可运行；Git 全程记录开发过程。 |
| **非目标**（明确不做） | 消息通知、评论互动、活动审核流、社团管理、签到考勤（取舍依据见《01-需求分析.md》2.3）。 |
| **重要约束**（遵守什么规则） | ① 角色权限：学生仅可浏览与报名，教师仅可管理自己发布的活动；② 业务规则：报名不超上限、活动开始后不可报名、同人不可重复报名；③ 安全：密码哈希存储、仓库不提交敏感信息；④ IDE 受控：AI 产出仅作候选，须经工程事实（代码差异/构建/测试/人工确认）验证后才合并；⑤ Git 规范：分阶段提交、提交信息说明修改内容。 |
| **完成依据**（怎么算达标） | ① REQ-01~08 均有对应 TEST 用例且全部通过；② 核心业务过程"教师发布活动 → 学生浏览并报名 → 教师查看报名情况"可完整走通；③ Git 提交记录真实反映演进过程；④ 实验报告与代码、仓库内容一致。 |

## 使用方式

- 本意图在编码前形成，是后续设计（03 阶段）、实现（04 阶段）和验证（05 阶段）的依据；
- 开发中发现原有理解有问题时，先重新判断需求与工程意图，再决定如何修改软件，不直接按 AI 建议扩大或改变实现范围。

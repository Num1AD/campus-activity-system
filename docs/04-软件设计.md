# 04 软件设计 —— 校园活动管理系统 V1.0

> 来源：实验一实验要求"（三）软件设计" + 报告模板"四、软件设计"（4.1~4.4）
> 依据：docs/01-需求分析.md（REQ-01~08）、docs/02-工程意图.md、docs/03-决策记录.md

## 4.1 总体设计

### 总体结构

采用**前后端分离**结构，三层组织：

| 层 | 组成 | 职责 |
|---|---|---|
| 前端层 | Vue3(CDN) 单页应用（HTML + JS + CSS） | 页面渲染、表单校验、调用 REST API |
| 后端层 | FastAPI（Python） | 提供 REST API、业务逻辑、权限校验、认证 |
| 数据层 | SQLite（单文件数据库） | 持久化存储 users / activities / registrations 三张表 |

部署方式：FastAPI 同时托管前端静态文件（同源部署），浏览器访问一个端口即可，避免 CORS 跨域问题。

### 模块划分

| 模块 | 主要功能 | 对应需求 |
|---|---|---|
| 用户模块 | 注册（学号/工号+密码+角色，仅学生/教师）、登录、token 认证、角色识别 | REQ-01、REQ-02、REQ-10 |
| 活动模块 | 教师发布活动、编辑、取消；活动列表/详情（含剩余名额）；状态管理 | REQ-03、REQ-04、REQ-05、REQ-08 |
| 报名模块 | 学生报名、取消报名、"我的活动"、教师查看报名情况 | REQ-06、REQ-07 |
| 管理模块 | 管理员查看全部账号、禁用/启用、删除（不可操作自己） | REQ-09 |

模块间依赖：活动、报名、管理模块都依赖用户模块（登录与角色识别）；报名模块依赖活动模块（校验活动状态与名额）；管理模块仅面向 admin 角色。

## 4.2 核心业务流程

### 流程一：学生浏览活动并报名（对应 REQ-05/06/07）

1. 学生打开系统，浏览活动列表（未登录可浏览，REQ-05 决策）；
2. 点击活动查看详情（时间、地点、剩余名额）；
3. 点击"报名"→ 要求登录 → 校验：活动状态为报名中、未重复报名、名额未满（REQ-08）；
4. 报名成功 → 名额减 1 → "我的活动"中可见该活动；
5. 学生可取消报名 → 名额释放。

### 流程二：教师发布并管理活动（对应 REQ-03/04）

1. 教师登录后进入管理页；
2. 填写活动信息（名称、时间、地点、人数上限、描述）→ 发布；
3. 学生端立即可见该活动；
4. 教师可查看自己发布活动的报名人数，可编辑活动信息、可取消活动（取消后学生不可再报名）。

## 4.3 数据设计

### 实体关系

三张表：`users`（用户）1 —— N `activities`（活动）1 —— N `registrations`（报名记录）
一个教师可发布多个活动；一个活动可被多个学生报名；一个学生可报名多个活动（同一活动仅一次）。

### 数据表设计

| 数据对象/表 | 关键字段 | 主要用途 | 与其他数据的关系 |
|---|---|---|---|
| users（用户表） | id、username（学号/工号）、name（姓名）、password_hash（密码哈希）、role（student/teacher/admin）、is_active（账号状态，1=正常 0=禁用）、created_at | 注册登录、角色识别、账号管理 | activities.creator_id → users.id；registrations.user_id → users.id |
| activities（活动表） | id、title、description、location、start_time、end_time、capacity（人数上限）、creator_id、created_at | 活动发布与管理、列表/详情展示 | creator_id → users.id（发布者）；被 registrations.activity_id 引用 |
| registrations（报名表） | id、activity_id、user_id、created_at | 报名记录、我的活动、人数统计 | activity_id → activities.id；user_id → users.id；UNIQUE(activity_id, user_id) 约束防重复报名 |

### 业务规则在数据层的落实

- 重复报名：`registrations` 表对 (activity_id, user_id) 建 UNIQUE 唯一约束，数据库层面兜底；
- 名额限制：报名接口事务内检查 `已报名人数 < capacity`，并发下仍安全；
- 密码安全：密码不存明文，存 SHA-256 加盐哈希（见 4.4 决策 3）；
- 账号禁用：users.is_active=0 的账号登录被拒（决策 7）。

## 4.4 关键设计决策

| 序号 | 设计决策 | 理由 |
|---|---|---|
| 1 | **角色权限控制**：教师仅可发布/管理自己创建的活动；学生仅可浏览与报名；管理员仅可管理账号；后端每个接口校验角色与归属 | 对应 REQ-03/04/05/06/09；权限放在后端而非前端，防止绕过前端直接调 API |
| 2 | **重复报名与名额约束**：数据库 UNIQUE(activity_id,user_id) + 报名事务内检查名额 | 对应 REQ-08；数据库约束 + 业务检查双保险，保证超员/重复报名被拒绝 |
| 3 | **密码加盐哈希存储**：SHA-256 + 随机盐，不存明文 | 对应工程意图安全约束；即使数据库泄露也无法直接还原密码 |
| 4 | **认证采用内存 token**：登录成功签发随机 token，服务端内存维护 token→用户映射（重启后需重新登录） | 实验规模避免引入 JWT 等重依赖；README 中说明局限；未来可平滑升级为 JWT |
| 5 | **同源部署**：FastAPI 托管前端静态文件，前后端同端口访问 | 免 CORS 配置，部署简化，本地一键运行 |
| 6 | **活动状态规则**：活动开始时间即报名截止；教师可手动取消活动；"报名中/已截止/已取消"三态由时间+手动标记动态计算 | 支撑 REQ-08；不引入复杂状态机，与决策记录中"活动三态"一致 |
| 7 | **管理员角色与账号管理**：role 增 admin（系统预置，注册不开放）；users 增 is_active；管理接口仅 admin 可调且不可操作自己；被禁用账号登录被拒 | 对应 REQ-09/10；注册不开放 admin 防越权；禁用作状态标记而非物理删除，保留审计可能；管理员不介入活动审核（保留教师信任） |

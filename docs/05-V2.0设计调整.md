# 05 V2.0 设计调整 —— 校园活动管理系统 V2.0

> 定位：`docs/01`~`04` 是**实验一（V1.0）阶段**的设计文档，保留作为迭代基线；本文件记录实验二由用户访谈驱动的设计调整。
> 依据：报告第四、六章（需求与用户故事）、第七章（变更与影响分析）、第八章（设计调整），字段与接口均按当前代码核对。
> 需求编号：R-01~R-08 对应报告第四章；US-01~US-08 对应报告第六章。

## 5.1 本轮设计为什么调整

V1.0 的报名是"提交即生效、满员即拒绝"。V2.0 通过三个角色的访谈确认了四条此前缺失的规则，它们互相牵连，构成一次完整的设计调整：

| 需求 | 来源角色 | 对设计的影响 |
|---|---|---|
| R-01 满员后进入候补而非被拒 | 学生（现象）→ 教师（规则） | 报名表需要状态字段；满员分支由拒绝改为入队 |
| R-02 候补按进入候补的时间排序 | 教师 | 需要单独记录进入候补的时刻，不能复用报名时间 |
| R-03 报名状态需要区分并展示 | 学生 | 状态口径贯穿接口与前端；活动状态与报名状态要分开表达 |
| R-04 名额空出后由队首候补递补 | 教师 | 取消报名与递补须在同一事务内完成 |
| R-05 候补可主动退出、其后依次前移 | 教师 | 退出要按状态分支处理 |
| R-06 教师可设参加资格与是否需要审核 | 教师 | 活动表需要两个新字段；报名增加待审核状态 |
| R-07 审核顺序为先资格、后名额 | 教师（追问所得） | 审核通过后按当时剩余名额决定正式参加或进入候补 |
| R-08 管理员管账号与平台活动 | 管理员 | 角色由两种扩为三种；新增账号可用状态与管理员模块 |

## 5.2 数据设计调整

### 字段变化（对照 V1.0）

| 表 | V1.0 | V2.0 新增 / 变更 |
|---|---|---|
| `users` | role 取值 student / teacher | role 取值扩为 **student / teacher / admin**；新增 **is_active**（账号是否可用） |
| `activities` | 无审核与资格相关字段 | 新增 **require_review**（是否需要审核报名）、**eligibility**（参加资格说明） |
| `registrations` | 只有 id / activity_id / user_id / created_at | 新增 **status**（报名状态）、**queued_at**（进入候补的时间） |

### 完整表结构（V2.0，与 `backend/database.py` 一致）

| 数据对象/表 | 关键字段 | 主要用途 |
|---|---|---|
| users（用户表） | id、username（学号/工号）、name、password_hash、**role（student / teacher / admin）**、**is_active**、created_at | 注册登录、角色识别、账号启停 |
| activities（活动表） | id、title、description、location、start_time、end_time、capacity、**require_review**、**eligibility**、creator_id、is_cancelled、created_at | 活动发布与管理、审核开关与资格说明 |
| registrations（报名表） | id、activity_id、user_id、**status（pending / confirmed / waitlisted）**、**queued_at**、created_at | 报名记录、状态展示、候补队列排序 |

原有约束不变：三张表的外键关系、`registrations` 上的 `UNIQUE(activity_id, user_id)`（防重复报名）、`capacity > 0` 检查。

### 名额口径调整（关键）

**已报名人数由「报名记录总数」改为「只统计正式参加（status = confirmed）」**。候补与待审核记录不占用名额。

这一条牵动了所有用到人数的地方：剩余名额计算、满员判断、编辑活动时"人数上限不得小于已报名人数"的校验口径。若沿用旧口径，候补会被算作占位，导致剩余名额偏少、明明有空位的活动被判成已满（对应 BUG-18）。

## 5.3 业务流程调整

### 报名流程（新增审核分支）

1. 学生提交报名，系统校验活动状态与是否重复报名（与 V1.0 一致）；
2. 若该活动设置了需要审核，报名进入**待审核**，不直接确定结果；
3. 教师审核本人活动收到的报名，可通过或拒绝；拒绝则该报名不能参加本活动；
4. 无需审核或审核通过的报名，再判断剩余名额：**有名额转为正式参加，名额已满则进入候补队列**。

### 取消与递补流程（V2.0 新增）

1. 正式参加的学生取消报名，释放一个位置；
2. 若该活动存在候补，**队列最靠前的候补学生转为正式参加**，其余候补顺序不变；
3. 候补学生主动退出时，其后的候补依次前移，**正式参加人数不变**；
4. 取消与递补在**同一事务内**完成，避免并发下漏补或多补。

报名与递补的完整状态流转见图 8-1（见实验报告第八章，源文件 `report/images/fig_8_1_flow.png`）。

## 5.4 状态与规则

### 活动状态：沿用 V1.0 的三态

报名中 / 已截止 / 已取消，按当前时间与 `is_cancelled` 动态计算。**不新增「已满」状态**——满员通过剩余名额为 0 体现，学生的结果由报名状态表达。

### 报名状态：V2.0 新增的三态

| 状态 | 含义 | 产生的时机 |
|---|---|---|
| 待审核 | 需审核活动的报名提交后，结果尚未确定 | 提交时活动需审核 |
| 正式参加 | 已确定参加，占用一个名额 | 无需审核且有名额；或审核通过且有名额 |
| 候补中 | 等待空余位置 | 提交时名额已满；或审核通过但名额已满 |

### 关键规则

1. **名额口径**：正式参加人数只统计 `confirmed`，候补与待审核不占用名额；
2. **递补触发**：正式报名取消与递补在同一事务内完成；
3. **队列顺序**：候补按 `queued_at` 升序排列，作为递补的唯一依据（不复用报名时间 `created_at`）；
4. **判断顺序**：先确认资格（审核），再看剩余名额，两个判断不合并；
5. **账号停用**：停用后的账号不能登录，**已签发的登录凭证同时失效**；账号状态只影响登录，不改变该账号已发布的活动与已提交的报名记录；
6. **权限边界**：管理员的写操作限于账号状态与活动状态，不参与具体报名业务的处理；报名与候补名单可只读查看用于监督（属设计约定，见报告第八章第 7 条）。

## 5.5 接口调整（对照 V1.0）

### 新增接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/activities/{id}/registrations/{student_id}/review` | 教师审核本人活动收到的报名；通过后按剩余名额定正式或候补 |
| GET | `/api/admin/users` | 管理员查看平台账号（含三种角色） |
| POST | `/api/admin/users/{id}/status` | 管理员停用 / 恢复账号（不能停用自己） |
| POST | `/api/admin/activities/{id}/cancel` | 管理员从平台层面处置违规活动 |

### 行为变更的接口

| 方法 | 路径 | 变化 |
|---|---|---|
| POST | `/api/activities/{id}/register` | 满员时不再返回"报名人数已满"，改为进入候补队列；需审核的活动返回待审核 |
| DELETE | `/api/activities/{id}/register` | 按状态分支：正式参加取消后触发递补；候补退出后其后依次前移 |
| GET | `/api/my-activities` | 学生侧返回报名状态（含状态中文名与进入候补时间） |
| GET | `/api/activities/{id}/registrations` | 名单按待审核 / 正式参加 / 候补中分组排序；管理员可只读查看（返回 `readonly` 标记） |
| GET / POST / PUT | `/api/activities`、`/api/activities/{id}` | 请求与响应增加 `require_review`、`eligibility` |

### 路径不变的部分

登录注册（`/api/register`、`/api/login`、`/api/me`、`/api/logout`）、活动列表与详情、活动发布与取消的路径均与 V1.0 一致，V1.0 的功能全部保留可用。

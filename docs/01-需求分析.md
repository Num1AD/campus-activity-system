# 01 需求分析 —— 校园活动管理系统 V1.0

> 来源：实验一《基于工程意图的软件迭代开发》实验要求 + 实验报告模板"二、需求分析"
> 对应报告章节：2.1 业务问题与用户目标 / 2.2 V1.0 需求 / 2.3 需求取舍与范围控制

## 2.1 业务问题与用户目标

**业务问题**：校园活动目前主要靠线下通知、班级群转发和人工统计报名，存在三个痛点：

1. 活动信息分散，学生难以及时发现和了解活动；
2. 报名依赖人工统计，效率低且容易出错；
3. 活动组织教师无法掌握报名情况，难以判断活动组织效果。

V1.0 要解决的问题是：**活动信息线上化 + 报名流程线上化**，打通"教师发布 → 学生浏览 → 报名参与 → 教师掌握情况"这一基本业务过程。

**用户与目标**：

| 用户 | 核心目标 | 对应能力 |
|---|---|---|
| 学生 | 及时看到学校有哪些活动、了解详情、报名参加、随时查看自己报名的活动 | 浏览活动、报名/取消报名、我的活动 |
| 活动组织教师 | 把活动信息发布出去、管理自己发布的活动、掌握报名人数 | 发布活动、编辑/取消活动、查看报名情况 |

## 2.2 V1.0 需求清单

| 需求编号 | 用户/角色 | 需求描述 | 优先级 | 验收依据 |
|---|---|---|---|---|
| REQ-01 | 所有用户 | 使用学号/工号 + 密码注册，注册时选择角色（学生/教师） | 高 | 注册成功后可凭账号登录 |
| REQ-02 | 所有用户 | 凭账号密码登录，登录后按角色进入对应功能 | 高 | 正确凭据登录成功；错误凭据被拒绝 |
| REQ-03 | 教师 | 发布活动：名称、时间、地点、人数上限、活动描述 | 高 | 发布成功后学生端可见该活动 |
| REQ-04 | 教师 | 管理自己发布的活动：查看列表与报名人数、编辑、取消 | 高 | 修改后学生端即时看到更新 |
| REQ-05 | 学生 | 浏览活动列表与详情（时间、地点、剩余名额） | 高 | 未登录也可浏览活动列表与详情 |
| REQ-06 | 学生 | 报名 / 取消报名活动 | 高 | 报名后"我的活动"出现该活动；取消后名额释放 |
| REQ-07 | 学生 | 查看"我的活动"及状态 | 中 | 列表与报名记录一致 |
| REQ-08 | 系统规则 | 名额约束与状态约束：报名不超上限；活动开始后不可报名；同人不可重复报名 | 高 | 超员/重复报名被系统拒绝 |

说明：8 条需求共同支撑"学生参与活动"的完整业务过程，不追求功能数量。

## 2.3 需求取舍与范围控制

以下候选需求经分析后**不进入 V1.0**：

| 候选需求 | 取舍决定 | 原因 |
|---|---|---|
| 消息通知（站内信/邮件提醒） | 不做 | 需要消息渠道集成，超出 V1.0"学生主动查看"的定位 |
| 活动审核流（发布需管理员审批） | 不做 | 会引入第三角色和审批状态机；V1.0 信任教师角色，发布即生效 |
| 评论互动、签到考勤、社团管理 | 不做 | 超出"发布 → 浏览 → 报名"核心业务链 |

原则：保证所确定的需求能形成一个合理的基本业务过程即可，不为增加功能数量而扩大系统范围。

### V2.0 实现结果（实验二迭代）

- **数据层**：`users` 角色扩展为 student/teacher/admin 并新增 `is_active`；`activities` 新增 `require_review`（是否需要审核）与 `eligibility`（参加资格）；`registrations` 新增 `status`（待审核/正式参加/候补中）与 `queued_at`（进入候补时间），并新增 `(activity_id, status)` 索引；
- **候补机制**（R-01~R-05）：满员报名转入候补队列并记录进入候补时间；正式参加者取消报名时队首候补自动递补；候补可主动退出、其后依次前移；已报名人数只统计正式参加，候补与待审核不占名额；
- **报名审核与参加资格**（R-06、R-07）：教师按活动设置审核开关与资格条件；报名经审核后按"先确认资格、再看剩余名额"判定，有名额转正式参加、满员进入候补；审核仅限本人活动；
- **管理员**（R-08）：查看平台全部账号及角色、停用异常账号并在处理后可恢复；停用后无法登录且已签发的会话立即失效；不能停用当前登录的管理员，不修改活动规则、不介入报名业务；
- **前端**：学生端报名状态标签与按钮文案（满员时提示"报名（进入候补）"）；教师端发布/编辑表单增加审核开关与参加资格，报名名单按状态分组并支持通过/拒绝；新增管理员账号管理视图；
- **代码规模**：后端新增 `routers/admin.py`，共 10 个 Python 模块；前端 3 个文件；
- **演示数据**：预置三条报名记录覆盖三种报名状态（待审核 / 正式参加 / 候补中），打开系统即可直接演示；演示活动过期时启动自动顺延；
- **验证**：`tests/test_api.py` 扩至 36 条全部通过；另有候补链路 21 项、审核与管理员 45 项、前端 21 项端到端验证脚本。

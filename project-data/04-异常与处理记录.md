## 本轮其他加固（非缺陷，提升稳健性）

1. `sqlite3.connect(..., check_same_thread=False)`：FastAPI 同步依赖在线程池执行、依赖收尾不保证同一线程，每个请求各持独立连接，关闭线程检查是安全的；
2. 报名事务由 `BEGIN` 改为 `BEGIN IMMEDIATE`：立刻取写锁，避免 deferred 事务"先读后写"时并发读到"未满"而相继写入造成超员；
3. `verify_password` 改用 `hmac.compare_digest` 做常量时间比较，消除摘要比对的时序侧信道；
4. 删除死代码 `auth._current_time()`；
5. 前端发布表单默认结束时间改为"开始 + 2 小时"（原先开始与结束同为默认值，直接点发布必被后端拒绝）。

## 经验沉淀

1. GitHub 502 多为服务端临时故障，先验证网络链路（fetch 成功即可排除本地问题）再重试；
2. 单人仓库 force push 用 `git push --force` 即可；多人协作必须用 `--force-with-lease` 防覆盖；
3. commit 作者在创建时固化，事后改需要 amend（改变 hash），如需改写务必在历史公开前完成；
4. Git 作者署名（user.name/email）与 GitHub 账号是两个独立概念，各自独立配置。
5. 界面元素错位要先量测再改样式。本次"卡片不等高"的直觉判断是错的——卡片早已被 Grid 拉齐，真正错位的在卡片内部。量到实际坐标（按钮分别在 y=397 / 331）才定位到问题的那一层。
6. 会改变被测系统状态的测试脚本，必须自己负责把前置条件恢复回来。否则第二次运行必然失败，而失败现象与真实功能缺陷很难区分，容易顺着错误的方向去改代码。
7. 测试数据不要与演示数据同名。测试脚本常见的"先删同名、再重建"清理逻辑，会把同名的演示数据一并覆盖掉，交作业时打开系统看到的就是测试数据而不是设计好的演示场景。
